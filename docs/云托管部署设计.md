# 微信云托管部署设计（Supabase 栈）

> 目标：把现有 Supabase 后端原样搬到微信云托管，客户端只改网络适配层，业务与数据库不动。
> 依据：`docs/后端部署方案对比.md`（方案 D）。

---

## 1. 整体形态

```
小程序  ──callContainer(HTTP)──►  服务 A：API（Kong → PostgREST / GoTrue / Storage / Functions）
        ──微信通道(WebSocket)──►  服务 A 内的 Realtime
                                  服务 B：Postgres（数据目录挂 CFS）
```

两个服务，环境内网互通；**公网访问关闭**，避免暴露面（默认域名只用于开发测试，不作为正式出口）。

---

## 2. 服务拆分

| 序号 | 云托管服务 | 内容 | 实例规格 | 说明 |
| --- | --- | --- | --- | --- |
| B1 | `db` | `supabase/postgres:15.x`（含 pgcrypto、uuid-ossp、pg_graphql 等） | 1 核 2 G | 数据目录挂 CFS |
| B2 | `api` | `kong` 作为入口，反代到 `postgrest` / `gotrue` / `storage-api` / `realtime` / edge functions | 1 核 2 G | 单容器内多进程，或用官方 compose 的 supervisord 方案 |

> 若一个容器跑多个组件过于勉强，可拆成 3 个服务（`rest`、`auth`、`rt`），单环境上限 15 服务，够用。

---

## 3. 端口与健康检查

| 服务 | 端口 | 健康检查 |
| --- | --- | --- |
| `db` | 5432（仅内网） | `pg_isready -U postgres` |
| `api` | 8000（云托管容器端口） | `GET /rest/v1/`（PostgREST 根路径返回 OpenAPI） |

云托管要求容器监听一个端口并对外提供 HTTP；Kong 的 8000 作为入口最贴近现状。

## 4. 环境变量清单

| 变量 | 用途 | 备注 |
| --- | --- | --- |
| `POSTGRES_PASSWORD` | 数据库密码 | 云托管密钥配置，勿写入仓库 |
| `POSTGRES_DB` | 库名 | `breakice` |
| `JWT_SECRET` | 签发/校验 | 长度 ≥ 32，替换掉默认值 |
| `ANON_KEY` / `SERVICE_ROLE_KEY` | 由 `JWT_SECRET` 签出的两个 JWT | 客户端只用 `ANON_KEY` |
| `PGRST_DB_URI` | PostgREST 连接串 | 指向 `db:5432` |
| `PGRST_JWT_SECRET` | 同上 | |
| `GOTRUE_SITE_URL` | 认证回调 | 可填占位 |
| `GOTRUE_JWT_SECRET` | 同上 | |
| `STORAGE_BACKEND` | `file` 或 `s3` | 建议 `s3` 指向 COS，避免占 CFS |
| `ANON_KEY`（客户端） | 小程序 `.env.local` | 迁移后替换 |

## 5. 持久化与备份

| 数据 | 位置 | 备份 |
| --- | --- | --- |
| Postgres 数据目录 | CFS 挂载到 `/var/lib/postgresql/data` | 每日 `pg_dump` 到 COS，保留 7 天 |
| 画作文件 | COS（`artworks` 桶） | 依赖 COS 版本控制 |
| 迁移记录 | 数据库内 `schema_migrations` | 随库备份 |

**必须验证的一件事**：容器重启后数据是否还在（CFS 挂载是否生效）。这是整个方案最容易翻车的地方，验收时必须实测。

## 6. 网络层适配（客户端）

### 6.1 HTTP：`uniRequest` → `callContainer`

改 `app/src/platform/supabase.ts` 里的传输函数，保持入参/返回结构不变：

```
uni.request({ url: `${baseUrl}${path}`, method, header, data })
  ↓
wx.cloud.callContainer({
  config: { env: '<云托管环境ID>' },
  path: path,            // 相对路径，例如 /rest/v1/rooms
  method, header, data,
})
```

要点：

| 项 | 处理 |
| --- | --- |
| `apikey` / `Authorization` | 原样放 header，PostgREST 照旧校验 |
| 超时 | callContainer 默认 60 s，AI 评分接口正好卡线，必要时拆成异步 |
| 错误结构 | callContainer 返回 `{ statusCode, data }`，与 `uni.request` 对齐后再走原有错误处理 |
| 保底 | 未配置云托管环境时，回退到 `uni.request`（便于本地/旧环境调试） |

### 6.2 WebSocket：Realtime

两条路，按实测取舍：

1. **云托管 WebSocket 通道**（`connectContainer`，官方文档有小程序端示例）
2. **降级为轮询**：现有代码本来就有 1–2 s 轮询兜底，实时通道只是加速

**验收标准**：即使 WebSocket 完全不工作，游戏也必须能玩（靠轮询）；实时通道只影响"顺滑度"。

## 7. 部署顺序

1. 建环境 → 建 `db` 服务 → 挂 CFS → 初始化（`initdb` 或使用镜像自带初始化）
2. 导入结构：按顺序执行 26 支迁移 + `supabase/local/00-supabase-shim.sql`（**仅本地验证用**，云上是真实 Supabase 镜像，不需要 shim）
3. 建 `api` 服务 → 配环境变量 → 起 Kong 与各组件
4. 关闭公网访问 → 配置 `callContainer` 白名单
5. 客户端改环境变量 → 跑一局四玩法联机
6. 打开「超限按量」，配置 CPU/内存告警与每日备份

---

## 8. 验收清单

| # | 检查 | 期望 |
| --- | --- | --- |
| 1 | 重启 `db` 容器 | 数据仍在（CFS 生效） |
| 2 | 重启 `api` 容器 | 客户端自动恢复，无需重进房 |
| 3 | 断网 10 秒后恢复 | 轮询补回状态，局面一致 |
| 4 | 4 人一局四玩法 | 全部正常 |
| 5 | AI 评分 | 60 s 内返回，超时有降级 |
| 6 | 公网直连默认域名 | 应当不可用（已关闭） |

---

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| CFS 挂载在云托管版本间行为不一致 | 先用最小验证：建表 → 重启 → 查数据 |
| 长连接经微信通道延迟高 | 保留轮询兜底；实测超过 2 s 才考虑优化 |
| 单容器跑多组件内存不足 | 拆成 3 个服务；或把 Storage 放 COS 减负 |
| 60 s 超时卡住 AI 评分 | 评分改异步：先落库占位，回调再更新 |
| 环境级 QPS 上限 | 观察后台指标；必要时提高套餐 |
