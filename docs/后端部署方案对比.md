# 后端部署三方案对比（云开发 / 云托管 / 境内 ECS）

> 用途：供讨论决定最终方案。核实时间：2026-11；信息来源见文末。
> 结论先行：**三个方案都能做到"正式发布且免自建服务器"，区别在改造量、成本模型与风险。**

---

## 1. 先对齐现状

| 项 | 现状 |
| --- | --- |
| 后端 | Supabase 云（境外）：PostgreSQL + RLS + Storage + Realtime(WebSocket) + 5 个 Edge Functions |
| 客户端 | `uni.request` 直连 REST（PostgREST），WebSocket 直连 Realtime |
| 域名 | Supabase 分配的境外域名，**无法备案、无法填进小程序合法域名** |
| 因此 | 体验版必须开「开发调试」才能联机；正式版直接不可用 |

**所有方案要解决的核心问题**：让正式版能合法访问后端。

---

## 2. 已核实的事实（带出处）

| # | 事实 | 影响 |
| --- | --- | --- |
| 1 | 云托管实例规格可选 0.25/0.5 → 1/2 → 2/4 → 4/8 … 16/32（核/GiB），默认 1 核 2 G | 跑自建 Supabase 需要 2 核 4 G，**规格是够的** |
| 2 | 一个环境下最多 **15 个服务、28 个实例**，服务间可内网调用 | 可以把 Postgres 拆成单独服务 |
| 3 | 云托管**支持 WebSocket**（官方有小程序端 WebSocket 文档） | `realtime.ts` 的思路可以保留 |
| 4 | 云托管请求超时 **60 s**、请求包体 **20 M** | AI 评分 60 s 上限刚好，需注意长任务 |
| 5 | 云托管默认域名"**仅可用于开发和测试**"，官方建议配自定义域名"以免被封" | **默认域名不能作为正式出口** |
| 6 | 小程序/公众号 H5 通过 `callContainer` 调用云托管，**不需要开通公网访问** | ← 这就是免备案的关键路径 |
| 7 | 云开发免费云环境 40,000 资源点/月（6 个月），基础套餐 ¥19.9/月 | 低用户量成本≈0 |
| 8 | 云托管按量计费需开启"超限按量"，否则服务会被停 | 部署时必开 |

**推论（最重要的一条）**：

> 云托管要免备案，必须让**所有请求走 `callContainer` / WebSocket 走微信通道**，
> 而不是直连 `https://默认域名`。
> 默认域名只适合开发调试，正式版走它既有封禁风险，也失去了"免域名"的意义。

这意味着方案 D 需要改**网络适配层**（`platform/supabase.ts`、`platform/realtime.ts`），
但**不需要改业务逻辑与数据库设计**。

## 3. 三方案对比

### 3.1 总览

| 维度 | B 云开发 | D 云托管 | C 境内 ECS |
| --- | --- | --- | --- |
| 正式发布免备案 | ✅ | ✅（走 callContainer） | ❌ 必须备案 15–20 天 |
| 要买服务器 | ❌ | ❌ | ✅ 2 核 4 G |
| 自己运维 | ❌ | ❌ | ✅ 备份/证书/监控/磁盘 |
| 数据库形态 | 文档型（需重构） | Postgres（原样） | Postgres（原样） |
| 表结构改动 | **26 张全改** | 0 | 0 |
| RLS 策略 | 换成安全规则（重写） | 原样保留 | 原样保留 |
| 实时通道 | 改 `watch` | WebSocket 保留，连接方式改 | 原样 |
| 网络层改动 | `wx.cloud` 全套 | 适配层改 `callContainer` | 改两个环境变量 |
| 成本模型 | 按调用次数（资源点） | 按实例时长 + 流量 | 固定月费 |
| 用户为 0 时成本 | ≈ 0 | ≈ 0（缩容） | **¥25–50/月照收** |

### 3.3 成本（估算，需以控制台为准）

| 场景 | B 云开发 | D 云托管 | C ECS |
| --- | --- | --- | --- |
| 0 用户（挂起） | ¥0 | ≈¥0（缩容到最小） | ¥25–50/月 |

## 4. 各方案的"坑"

### B 云开发
- **关系模型改文档模型是最大风险**：`rooms → room_members → games → game_secrets → artworks` 是强关联，文档库没有 join，要么嵌套（撞大小与并发限制），要么在云函数里手工拼装（代码量翻倍）。
- 云函数冷启动 1–3 s，**开局瞬间会顿**。
- 现有 313 个测试里，凡是断言 SQL/表结构的都要重写。

### D 云托管
- 必须改网络层为 `callContainer`，否则免备案不成立。
- **数据库跑在容器里不是生产级方案**：容器重启、扩缩容都会影响数据目录，必须挂 CFS 持久化 + 定时 `pg_dump` 到 COS。
- 单环境 28 实例上限、环境级 QPS 上限，用户暴涨时受限。
- Realtime 长连接经过微信通道，实际延迟需实测。

### C 境内 ECS
- **备案 15–20 天**是硬等待，且主体必须与小程序一致。
- 运维全自己扛：备份、证书续期、磁盘、监控、安全组。
- 但**改动最小、风险最低**，且代码完全可控。

## 5. 一句话判断

| 你的优先级 | 选 |
| --- | --- |
| 不想重写后端、要我少踩坑 | **D**（改适配层，不动业务） |
| 想彻底不碰服务器、也不介意重写后端 | B（但要接受 3 周重写 + 冷启动） |
| 想要最可控、最便宜的固定成本、能等 20 天 | **C** |

**我的倾向：D 为主，C 为兜底。**

理由：D 保住了已验证的数据库设计与 RLS（这是最难重建的部分），代价只是把网络层换成 `callContainer`；如果 D 在实测中遇到不可解的问题（比如长连接延迟不可接受），退回 C 的成本很低——镜像已经做好了，换个地方跑而已。

B 唯一明显优势是"完全不碰服务器"，但代价是把关系型数据全部重构，风险与工期都最高。

## 6. 决策前建议先做的一次小验证（半天）

不管选哪个，有一步验证对三者都有价值：

```
在本机用 docker 起自建 Supabase（Postgres + PostgREST + Realtime + Storage）
→ 跑通 26 支迁移
→ 客户端只改环境变量跑一局
```

- 若选 **D**：验证通过后，把同一套 compose 搬到云托管即可
- 若选 **C**：搬到 ECS
- 若选 **B**：也能确认现有逻辑的边界，便于评估重写量

这一步不花钱、不动线上，却能排除"迁移后跑不起来"的最大不确定性。
