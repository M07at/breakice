# 你画我猜联机方案

## 为什么不能直接换后端

`DrawRoomBackend` 接口（`view/subscribe/submitDrawing/tick/sendMessage/sendReaction/dispose`）
本身是 Promise 化的，看着像给远程实现准备的。但 `pages-draw/play.vue` 除了接口，
还直接用了本机实现专有的成员：

| 页面用法 | 说明 |
| --- | --- |
| `room.actor` / `room.viewer` | 当前作画者与观战者的 `DrawEngine`（本机对象） |
| `room.pump` | 笔画分片泵，需要本机 `StrokeTransport` |
| `room.onStrokeChange` | 画布重绘回调 |
| `room.settings` | 重开一局用 |

所以"把 `LocalDrawRoomBackend` 换成远程实现"不是替换一个对象就能完成的，
页面里这三类东西也要一起抽象。

## 已完成的底座（0017）

采用**主持人权威 + 指令队列**模型，不改 B 的引擎：

```
draw_sessions   一个房间一条：存权威视图 view(jsonb) + version
draw_inbox      其他人的操作队列：submitDrawing / message / reaction / tick
```

| RPC | 谁可以调 | 作用 |
| --- | --- | --- |
| `publish_draw_view(room_id, view)` | 主持人 | 发布视图，版本号自增 |
| `read_draw_view(room_id)` | 本房成员 | 读当前视图 |
| `post_draw_action(room_id, kind, payload)` | 本房成员 | 投一条操作 |
| `take_draw_actions(room_id, limit)` | 主持人 | 取走待处理操作（取走即消费，不会重复） |
| `clear_draw_session(room_id)` | 主持人 | 结束时清理 |

两张表都开 RLS 且没有策略，只能走 RPC。验收脚本：`npm run check:drawroom`
（发布 → 读取 → 投指令 → 取走 → 再取为空 → 权限边界，共 9 项）。

## 还要做的客户端部分

### 1. `services/drawRemote.ts`

- `createDrawPublisher(client)`：绑定当前房间，把本机 `LocalDrawRoomBackend` 的视图变化
  节流发布（例如 500ms 一次），并每 800ms 调一次 `take_draw_actions`，
  按 `kind` 分别喂给本机 backend 的 `submitDrawing / sendMessage / sendReaction / tick`。
- `createRemoteDrawRoom(hostId)`：实现 `DrawRoomBackend`，`view()` 走 `read_draw_view`，
  `subscribe` 用轮询 + Realtime poke；三个动作走 `post_draw_action`。

### 2. `play.vue` 的解耦

把 `room.actor` / `room.viewer` / `room.pump` / `onStrokeChange` 收成一个 `DrawSurface`：

- 本机权威：现在的实现不动
- 非权威端：`actor` 只在"轮到我画"时可用（本机引擎 + 分片广播），`viewer` 用权威视图里的
  画作快照（`imageRef`）渲染，不需要笔画流

> 取舍：非权威端不追求笔画级实时，只在交画后看到成品图。
> 这与融合玩法（你画我猜谁是卧底）的体验一致，也避免把 60 帧笔画协议搬到轮询上。

### 3. 房间页入口

主持人开局时：先 `clear_draw_session` → 本机 `startLocalDrawRoom` → `createDrawPublisher`
→ 其他人 `read_draw_view` 拿到视图后进入观战/自己的回合。

## 关键阻碍：B 的引擎不认外部玩家名单

`LocalDrawRoomOptions` 只接受人数：

```ts
export interface LocalDrawRoomOptions {
  playerCount: number           // 只有人数
  variant: DrawVariant
  customText?: string
  scorer?: AiScorer
  now?: () => number
  listItems?: () => Promise<BankItem<'draw'>[]>
}
```

引擎内部按人数生成「我 / 玩家2 / 玩家3」这类虚拟玩家与其 id。后果有三个，都是联机绕不过去的：

1. 权威视图里的 `players[].id` 与房间真实成员 id **对不上**，联机端无法判断"轮到我了没有"；
2. 消息的 `playerId` 属于虚拟玩家，界面上认不出是谁说的；
3. 交画只能由"当前作画者"发起，而虚拟身份与真实登录身份没有映射。

**必须先做的最小改动**：给 `DrawRoomOptions` 增加可选的 `players?: { id: string; name: string }[]`，
有就用外部名单、没有才退回 `playerCount` 生成。这是一处向后兼容的扩展，不改变现有单机行为。

## 风险与取舍

| 点 | 说明 |
| --- | --- |
| 主持人掉线 | 视图停止更新；其他人会看到"等待主持人"，比静默卡住更容易理解 |
| 笔画实时性 | 非权威端只看成品图；要笔画级同步需要 Realtime broadcast + 分片序列，属后续优化 |
| 本地存储 | `LocalDrawRoomBackend` 的定时器仍跑在主持人设备上，不是服务端时钟 |
| 外部名单 | 见上一节，是接联机前必须补的扩展 |
| 验证方式 | 服务端已用脚本验收（9 项）；客户端需要两台设备，或开发者工具的多账号调试 |
