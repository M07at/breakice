> 目标：先产出一个**联机可用**的试玩版收集反馈，再逐步推进到微信小程序正式发布。
> 全程保证：随时能退回验收版并直接交给老师。

## 1. 回滚保障（只保底，不做常规演练）

### 1.1 什么时候用

回滚**不是**日常开发手段，只在两种情况下触发：

| 触发条件 | 处理 |
| --- | --- |
| **A. 严重瓶颈**：某条技术路线（如后端迁移）出现短期无法解决的阻塞，继续投入不划算 | 放弃该路线，回到验收版状态继续其他工作 |
| **B. 截止前不完整**：到了提交节点，新版本仍不够稳定/完整 | 直接把验收版交给老师检查 |

判断标准很明确：**新版本能不能完整跑完一局四玩法联机**。不能，就用验收版。

### 1.2 怎么用（三步，十分钟内完成）

```bash
# 1. 回到验收版
git checkout v1.0-验收版

# 2. 重装依赖并验证
cd app && npm ci && npm run verify

# 3. 出包
npm run build:mp-weixin      # → app/dist/build/mp-weixin
```

产物可直接用微信开发者工具导入，或上传为体验版交给老师。

### 1.3 凭什么保证能回滚

| 层 | 内容 | 状态 |
| --- | --- | --- |
| 代码 | git 标签 `v1.0-验收版`（本地 + Gitee 各一份） | ✅ 已完成 |
| 产物 | `mp-weixin` / `h5` 打包归档 + 源码 `git archive` | 阶段一完成 |
| 数据 | 数据库结构导出 + `supabase/rollback/*.sql` | 阶段一完成 |
| 配置 | 当时使用的环境变量取值快照（不含密钥明文） | 阶段一完成 |

> 归档放在本地与网盘（`backup/v1.0/`，不入仓库，因为体积大）。

### 1.4 提交前的固定动作

到提交节点时，无论新版本进度如何，都执行一次"能不能交"的检查：

```
新版本能否完整跑完一局联机？能 → 交新版；不能 → 交验收版
```

这一步写进流程，但不做定期演练，避免把时间花在不会发生的场景上。

## 2. 阶段一：联机可行性判断（第 1 天）

**目的**：确定"外部玩家怎么试玩"，这决定后面所有安排。

联机是这个作品的核心，试玩必须能测联机。因此先回答两个问题：

1. 小程序体验版能否支持多人联机？—— 可以，微信原生支持，只需把玩家加为体验成员。
2. H5 能否支持多人联机？—— **不确定**：H5 没有微信登录，项目当前用本地身份兜底（`LOCAL_USER_ID`），后端是否接受这种身份需要实测。

**做法**：

```bash
cd app && npm run build:h5
# 起本地静态服务，用两个浏览器标签（其中一个用无痕窗口）进同一房间
```

**分叉**：

| 结果 | 结论 |
| --- | --- |
| 两个标签能进同一房间并互相看到操作 | H5 可用，可作试玩辅助通道 |
| 进不去 / 后端拒绝本地身份 / 无法同步 | **直接砍掉 H5**，不再投入，试玩只走体验版 |

**硬规则**：H5 只在"联机可用"的前提下才做。联机不通就停，不做单机版 H5。

---

## 3. 阶段二：试玩版交付（第 2–3 天）

**目的**：让不在项目组的人能玩到、能测联机。

### 3.1 主通道：微信体验版

1. 上传代码 → 后台设为体验版。
2. 添加体验成员（名额以后台显示为准：个人主体较少，企业主体更多）。
3. 每位试玩者扫体验版二维码，用自己微信加入同一房间。

体验版的价值：**联机行为与正式版完全一致**，包括实时通道、扫码进房、掉线重连。

### 3.2 辅助通道（仅在阶段一判定 H5 可用时）

把 `app/dist/build/h5` 传到静态托管，拿到链接发群。作用是快速拉样本，但**不作为联机稳定性的判断依据**。

### 3.3 试玩说明

一页纸说清三件事：怎么进（扫码/链接）、怎么开局（房主建房 → 其他人输房间号或扫码 → 全员准备 → 开局）、出问题找谁。

**完成标志**：至少 4 个人在不同设备上，通过体验版完整玩完一局。

---

## 4. 阶段三：反馈收集与修复（第 1–2 周）

**目的**：把"能玩"变成"玩得稳"。

### 4.1 只重点收集联机相关反馈

问卷三问，全部围绕联机：

1. 有没有出现"看不到别人操作 / 画面不动"？
2. 有没有出现掉线、卡住、必须退出重进？
3. 这一局有没有完整走完（结算页正常出现）？

另加一个自由填写框。

### 4.2 修复优先级（严格按此顺序）

```
P0 联机正确性：同步丢失、状态不一致、卡在某一阶段、无法退出
P1 流程完整性：开局失败、结算异常、返回大厅异常
P2 玩法细节：计分、提示、文案
P3 视觉与动效
```

P0 没清完之前，不动 P2/P3。

### 4.3 已知风险点（历史出现过，重点回归）

| 现象 | 根因类别 |
| --- | --- |
| 观战画布空白 | 实时分片丢失，靠定时全量快照自愈 |
| 卡在 reveal 看不到结算 | 结束瞬间停发布器导致终态没发出去 |
| 退出后又被拉回结算页 | 自动进入逻辑与主动退出标记冲突 |
| 房主结束卡死 | 服务端局次已自然结束时收尾被异常中断 |

**完成标志**：连续 10 局联机（4 人）无 P0 问题。

---

## 5. 阶段四：后端迁移到境内（第 2–4 周）

**目的**：为正式发布扫清唯一的硬障碍——微信正式版要求服务器域名可备案，而 Supabase 云在境外，无法备案。

### 5.1 先本机验证（不花钱，不动线上）

1. 在**独立目录**起 docker-compose 版 Supabase（Postgres + PostgREST + GoTrue + Realtime + Storage + Kong）。
2. 按编号顺序执行 26 支迁移。
3. 客户端只改 `.env.local` 两个变量，跑一局联机。

**完成标志**：自建实例上四玩法能跑完一局，数据能落库。

### 5.2 再上云验证

- 申请阿里云 ECS 试用（香港，2 核 4 G，按量付费，按需开机）。
- 把 5.1 的 compose 原样搬上去，绑域名、配 HTTPS、跑联机。

**注意**：试用机是**按量付费实例，不满足备案要求**，只能用于验证，不能作为正式发布后端。

### 5.3 正式环境

| 项 | 建议 |
| --- | --- |
| 地域 | 中国大陆（华东/华北），只有境内节点能备案 |
| 规格 | 2 核 4 G 起步（自建 Supabase 空闲占 1.5–2.5 G），系统盘 60 G SSD |
| 计费 | 包年包月（备案要求，且比按量便宜） |
| 数据库 | 数据量上来后换 RDS 托管，避免自建单点 |
| 存储 | 画作文件转 OSS，ECS 只留数据库与业务 |
| 备份 | 每日 `pg_dump` 推 OSS，保留 7 天 |

**完成标志**：正式域名上能完整跑完一局，且断线重连正常。

---

## 6. 阶段五：合规与发布准备（第 3–5 周，与阶段四并行）

正式发布卡的是资质与配置，不是代码。

| 事项 | 说明 | 周期 |
| --- | --- | --- |
| **ICP 备案** | 主体必须与小程序主体一致；备案期间服务器可先用 | 15–20 天 |
| **域名** | 一个主域名即可，`api.xxx.com` 走子域 | 1 天 |
| **HTTPS 证书** | 免费证书即可，注意续期自动化 | 1 天 |
| **微信后台域名配置** | `request` / `socket` / `uploadFile` / `downloadFile` 四类都要填，**socket 最易漏** | 1 小时 |
| **小程序认证** | 企业主体 300 元/年；个人主体功能受限 | 1–3 天 |
| **类目与资质** | 含游戏玩法的小程序可能要求软著；建议按"工具/社交—聚会活动"申报并准备软著 | 1–4 周 |
| **隐私协议与用户协议** | 小程序必填项，缺了会被驳回 | 半天 |

**完成标志**：微信后台四类域名校验全部通过，提审材料齐备。

---

## 7. 阶段六：提审与发布（第 5–6 周）

1. 上传正式版 → 提交审核（附测试账号与操作说明）。
2. 被驳回时按意见修改，常见原因：类目不符、隐私协议缺失、功能与类目不一致。
3. 审核通过后可先灰度，观察 1–2 天再全量。
4. 全量发布。

**发布后的回退手段**（与前面的 git 回滚不同）：

- 微信后台支持"版本回退"到上一个线上版本，几分钟生效。
- 后端回滚：保留上一版本的迁移回滚脚本，配合 `pg_dump` 恢复。

**完成标志**：线上版本可被任意用户搜索/扫码使用。

---

## 8. 阶段七：发布后运营（持续）

| 事项 | 频率 |
| --- | --- |
| 联机异常日志巡检 | 每周 |
| 数据库备份校验（确认能恢复） | 每月 |
| 成本巡检（ECS / OSS / 流量） | 每月 |
| 版本迭代（小步发布） | 按需 |

**成本控制原则**：用户少时不上高配。单台 2 核 4 G 能支撑数百用户；流量与存储按量计费，用户不涨成本不涨。

## 9. 总时间线

```
第 1 天      阶段一：联机可行性判断（决定 H5 生死）
第 2–3 天    阶段二：体验版试玩版交付
第 1–2 周    阶段三：反馈收集与 P0 修复
第 2–4 周    阶段四：后端迁移（本机 → 试用云 → 正式环境）
第 3–5 周    阶段五：备案与发布准备（与阶段四并行）
第 5–6 周    阶段六：提审与发布
第 6 周起    阶段七：运营与迭代
```

关键路径是**备案（15–20 天）**，它是整条链上最长的等待项，应在阶段四一开始就提交。

```bash
# 回到验收版（提交给老师用这个）
git checkout v1.0-验收版 && cd app && npm ci && npm run verify && npm run build:mp-weixin

# 开发
cd app && npm run dev:mp-weixin
cd app && npm run build:mp-weixin   # → dist/build/mp-weixin
cd app && npm run build:h5          # 仅当 H5 联机验证通过后才用

# 提交前
```

**验收线**：每个阶段结束时 `npm run verify` 必须全绿；不绿就先修，不进入下一阶段。
