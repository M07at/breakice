# 技术推进计划（线性方案·至正式发布）

> 目标：先产出一个**联机可用**的试玩版收集反馈，再逐步推进到微信小程序正式发布。
> 全程保证：随时能退回验收版并直接交给老师。
> 本文件只描述技术步骤顺序，不涉及人员分工。

---

## 0. 起点

| 项 | 现状 |
| --- | --- |
| 代码 | `master`，已推送 Gitee |
| 基线标签 | `v1.0-验收版`（已创建并推送） |
| 后端 | Supabase 云：PostgreSQL + RLS + Storage + Realtime + 5 个 Edge Functions |
| 后端目标 | **微信云托管**（方案 D，见 0.2） |
| 前端 | uni-app 3 + Vue 3 + TS；`mp-weixin` 0.99 MB |
| 质量门 | 类型检查、313 个单元测试、构建、体积检查、密钥扫描、构建产物新鲜度 |

### 0.1 已决事项：H5 暂时舍弃

实测结论：H5 的联机链路可用（匿名身份 + 建房 + 加入 + 同步均正常），但**功能面与小程序的差异过多**，逐项对齐的成本远高于收益。

证据：

| 现象 | 原因 |
| --- | --- |
| 题库整体不可用 | H5 端连的是开发用的 mock 接口（`/__c1_mock/banks`），静态部署下不存在 |
| 扫码进房、分享、小程序码缺失 | H5 环境本身没有这些能力 |
| 部分页面分支不同 | 代码里有 `#ifndef H5` 的预览提示与独立的预览身份 |

**决定**：本计划不包含 H5。功能验证与试玩一律以**微信体验版**为准（体验版与正式版一致）。

**何时重新考虑 H5**：只有当"需要一次性把链接发给大量不特定用户"且体验成员名额成为瓶颈时才回头评估；届时需先补齐题库、画布、主持人控制台三处差异。

### 0.2 已决事项：后端迁到微信云托管（方案 D）

三个候选方案（云开发 / 云托管 / 境内 ECS）对比后选定 **D**，完整对比见 `docs/后端部署方案对比.md`。

选它的理由（按权重）：

| 理由 | 说明 |
| --- | --- |
| 保住已验证的后端 | Postgres、26 张表、RLS 策略、Realtime 全部原样，不重写业务 |
| 免备案 | 请求走 `callContainer`（微信通道），不需要域名、不需要 ICP 备案 |
| 免运维 | 不用买服务器、不用管证书续期与磁盘 |
| 按量计费 | 没人用时几乎不花钱，适合"先试玩、后发布"的节奏 |

**必须记住的三条约束**：

1. **不要用云托管的默认域名做正式出口**——官方标注它仅可用于开发和测试。
2. **HTTP 走 `callContainer`、实时走微信通道**，这是免备案成立的前提；改成直连 HTTPS 域名就前功尽弃。
3. **Postgres 数据必须挂 CFS + 每日 `pg_dump` 到 COS**，容器本身不保存数据。

**被排除的方案**：

| 方案 | 排除原因 |
| --- | --- |
| B 云开发 | 26 张关系表要改成文档型、RLS 要换成安全规则，改造量 22–32 人日，风险最高 |
| C 境内 ECS | 改造量最小但需备案 15–20 天且要自己运维；保留为**兜底方案**（见 5.5） |

## 1. 回滚保障（只保底，不做常规演练）

### 1.1 什么时候用

回滚**不是**日常开发手段，只在两种情况下触发：

| 触发条件 | 处理 |
| --- | --- |
| **A. 严重瓶颈**：某条技术路线（如后端迁移）出现短期无法解决的阻塞，继续投入不划算 | 放弃该路线，回到验收版状态继续其他工作 |
| **B. 截止前不完整**：到了提交节点，新版本仍不够稳定/完整 | 直接把验收版交给老师 |

判断标准很明确：**新版本能不能完整跑完一局四玩法联机**。不能，就用验收版。

### 1.2 怎么用（三步，十分钟内完成）

```bash
# 1. 回到验收版
git checkout v1.0-验收版

# 2. 重装依赖并验证
cd app && npm ci && npm run verify

# 3. 出包
npm run build:mp-weixin      # → app/dist/build/mp-weixin
```

产物可直接用微信开发者工具导入，或上传为体验版交给老师。

### 1.3 凭什么保证能回滚

| 层 | 内容 | 状态 |
| --- | --- | --- |
| 代码 | git 标签 `v1.0-验收版`（本地 + Gitee 各一份） | ✅ 已完成 |
| 产物 | `mp-weixin` 打包归档 + 源码 `git archive` | 阶段一完成 |
| 数据 | 数据库结构导出 + `supabase/rollback/*.sql` | 阶段一完成 |
| 配置 | 当时使用的环境变量取值快照（不含密钥明文） | 阶段一完成 |

> 归档放在本地与网盘（`backup/v1.0/`，不入仓库，因为体积大）。

### 1.4 提交前的固定动作

到提交节点时，无论新版本进度如何，都执行一次"能不能交"的检查：

```
新版本能否完整跑完一局联机？能 → 交新版；不能 → 交验收版
```

这一步写进流程，但不做定期演练，避免把时间花在不会发生的场景上。

## 2. 阶段一：试玩环境准备（第 1 天）

**目的**：把"能让外部玩家玩"这件事先搭起来。舍弃 H5 后，唯一通道是**微信体验版**。

### 2.1 打开体验版通道

1. 微信公众平台后台确认主体类型，查清**体验成员名额**（个人主体较少，企业主体更多）。
2. 把要试玩的微信号逐个加为体验成员。名额紧张时按批次轮换，不必一次加满。
3. 上传代码 → 后台「版本管理」→ 设为体验版。

### 2.2 设计一次 4 人试玩场次

联机必须 4 人才能测（谁是卧底与融合玩法下限），所以样本要按"场"组织，而不是散着发：

- 每场 4 人，其中 1 人当房主；
- 每场跑 2–3 局，覆盖四种玩法；
- 每场结束后当场填问卷（避免事后遗忘细节）。

体验成员名额有限时，用"多场次轮换"放大人数，而不是一次加很多人。

### 2.3 备份归档（同时完成）

按 1.3 的清单，把 `mp-weixin` 产物、源码、数据库结构、配置快照归档到 `backup/v1.0/`。

**完成标志**：体验版二维码可用；4 人能在不同设备上进入同一房间。

---

## 3. 阶段二：首轮试玩（第 2–3 天）

**目的**：拿到第一批真实反馈，重点是**联机**。

### 3.1 试玩说明（一页）

说清三件事：怎么进（扫体验版二维码）、怎么开局（房主建房 → 其他人输房间号或扫码 → 全员准备 → 房主选玩法）、出问题找谁。

### 3.2 现场观察比问卷更重要

每场安排一个人在旁边看，记录三类现象：

| 现象 | 记录什么 |
| --- | --- |
| 卡住 | 卡在哪个阶段、界面显示什么、是否必须退出重进 |
| 不同步 | 谁看不到谁、差了多久、刷新能否恢复 |
| 崩溃/白屏 | 复现步骤、机型 |

**完成标志**：至少完成 2 场（8 人次），且每种玩法都被玩到过。

---

## 4. 阶段三：反馈与 P0 修复（第 1–2 周）

**目的**：把"能玩"变成"玩得稳"。

### 4.1 问卷只问联机

1. 有没有出现"看不到别人操作 / 画面不动"？
2. 有没有出现掉线、卡住、必须退出重进？
3. 这一局有没有完整走完（结算页正常出现）？

另加自由填写框。

### 4.2 修复优先级（严格按此顺序）

```
P0 联机正确性：同步丢失、状态不一致、卡在某一阶段、无法退出
P1 流程完整性：开局失败、结算异常、返回大厅异常
P2 玩法细节：计分、提示、文案
P3 视觉与动效
```

P0 没清完之前，不动 P2/P3。

### 4.3 已知风险点（历史出现过，重点回归）

| 现象 | 根因类别 |
| --- | --- |
| 观战画布空白 | 实时分片丢失，靠定时全量快照自愈 |
| 卡在 reveal 看不到结算 | 结束瞬间停发布器导致终态没发出去 |
| 退出后又被拉回结算页 | 自动进入逻辑与主动退出标记冲突 |
| 房主结束卡死 | 服务端局次已自然结束时收尾被异常中断 |

**完成标志**：连续 10 局联机（4 人）无 P0 问题。

---

## 5. 阶段四：后端迁移到微信云托管（第 2–4 周）

**目的**：为正式发布扫清唯一的硬障碍——Supabase 云在境外、域名无法备案，正式版请求会被拦。

**选型已定：方案 D（微信云托管）**，详见 `docs/后端部署方案对比.md`。核心思路：

```
保留现有 Supabase 全套（Postgres + PostgREST + GoTrue + Realtime + Storage + Kong）
→ 打成容器跑在云托管
→ 小程序端改为 callContainer（HTTP）与微信通道（WebSocket）
```

**为什么这样能免备案**：`callContainer` 走微信通道，不经过「request 合法域名」校验，也不需要使用云托管的默认域名（官方标注默认域名仅可用于开发和测试）。

### 5.1 本机验证（不花钱、不动线上）

1. 在**独立目录**起 docker-compose 版 Supabase。
2. 按编号顺序执行 26 支迁移。
3. 客户端只改 `.env.local` 两个变量，跑一局联机。

**完成标志**：自建实例上四玩法能跑完一局，数据能落库。

> 这一步对三个候选方案都有价值；即使云托管后续出问题，这套 compose 也能直接搬到 ECS。

### 5.2 容器化与网络层适配

| 工作 | 内容 |
| --- | --- |
| 拆分服务 | Postgres 单独一个服务；PostgREST + GoTrue + Realtime + Storage + Kong 合并为另一个服务（单环境上限 15 服务、28 实例，够用） |
| 持久化 | Postgres 数据目录挂 **CFS**；画作文件走 **COS** |
| HTTP 适配 | `platform/supabase.ts` 的 `uniRequest` 改为 `callContainer`，保持入参/返回结构不变 |
| WebSocket 适配 | `platform/realtime.ts` 改为云托管通道；**注意不做长连接时要有轮询兜底**（现有代码已有） |
| 环境变量 | 库连接串、JWT 密钥、`ANON_KEY` 等移入云托管环境变量 |

**完成标志**：本地/云上跑同一套 compose，小程序能完成一局联机。

### 5.3 部署到云托管

| 项 | 设置 |
| --- | --- |
| 规格 | **2 核 4 G**（自建 Supabase 空闲占 1.5–2.5 G；0.25/0.5 档跑不动） |
| 计费 | 按量，**必须开启「超限按量」**，否则服务会被停 |
| 公网访问 | 关闭（走 callContainer 不需要），减少暴露面 |
| 备份 | 每日 `pg_dump` 到 COS，保留 7 天 |
| 监控 | 打开实例 CPU/内存与请求耗时的告警 |

**完成标志**：公网关闭的前提下，小程序通过 `callContainer` 能完整跑完一局。

### 5.4 数据迁移与验收

1. 从 Supabase 云 `pg_dump` 导出，导入云托管上的 Postgres。
2. 画作文件迁到 COS。
3. 用体验版跑 3 局（4 人），对比迁移前后的行为差异。

**完成标志**：连续 3 局无 P0；实时同步延迟与迁移前无明显退化。

### 5.5 兜底路径

若阶段四出现短期无法解决的阻塞（例如长连接延迟不可接受、CFS 数据不安全），按 1.1 的规则处理：

| 情况 | 处理 |
| --- | --- |
| 云托管可用但不够稳 | 保留现有 Supabase 云 + 体验版「开发调试」维持试玩，同时退回方案 C（ECS + 备案） |
| 云托管完全走不通 | 退回 C；镜像与 compose 已就绪，搬迁成本低 |

**注意**：不要因为"已经投入了"就硬撑——1.1 里写明"严重瓶颈就放弃路线"，这是预先约定的规则。

## 6. 阶段五：合规与发布准备（第 3–4 周，与阶段四并行）

选 D 之后，**ICP 备案不再是必经步骤**（请求走微信通道），但发布审核的其它门一样要过。

| 事项 | 说明 | 周期 |
| --- | --- | --- |
| **小程序认证** | 企业主体 300 元/年；个人主体功能受限 | 1–3 天 |
| **类目与资质** | 含游戏玩法的小程序可能要求软著；建议按"工具/社交—聚会活动"申报并准备软著 | 1–4 周 |
| **隐私协议与用户协议** | 小程序必填项，缺了会被驳回 | 半天 |
| **ICP 备案** | **D 方案不需要**。仅当以后要给 Web/H5 或第三方提供自定义域名时才需要（15–20 天） | — |
| **自定义域名** | **不需要**。云托管默认域名仅用于开发测试，正式调用走 callContainer | — |
| **微信后台域名配置** | **不需要**（callContainer 不校验域名） | — |

**完成标志**：认证通过、类目与隐私协议齐备、提审材料准备好。

> 若将来改用自定义域名（例如要给浏览器端用），才需要补备案与四类域名配置——届时按原来的 C 方案流程执行。

## 7. 阶段六：提审与发布（第 5–6 周）

1. 上传正式版 → 提交审核（附测试账号与操作说明）。
2. 被驳回时按意见修改，常见原因：类目不符、隐私协议缺失、功能与类目不一致。
3. 审核通过后可先灰度，观察 1–2 天再全量。
4. 全量发布。

**发布后的回退手段**（与前面的 git 回滚不同）：

- 微信后台支持"版本回退"到上一个线上版本，几分钟生效。
- 后端回滚：保留上一版本的迁移回滚脚本，配合 `pg_dump` 恢复。

**完成标志**：线上版本可被任意用户搜索/扫码使用。

## 8. 阶段七：发布后运营（持续）

| 事项 | 频率 |
| --- | --- |
| 联机异常日志巡检 | 每周 |
| 数据库备份校验（确认能恢复） | 每月 |
| 成本巡检（云托管实例时长 / COS / 流量） | 每月 |
| 版本迭代（小步发布） | 按需 |

**成本控制原则**：用户少时不上高配。2 核 4 G 的云托管实例能支撑数百用户；按量计费，没人用几乎不花钱。

## 9. 总时间线

```
第 1 天      阶段一：试玩环境准备（体验成员 + 体验版 + 归档）
第 2–3 天    阶段二：首轮试玩（2 场，4 人/场）
第 1–2 周    阶段三：反馈与 P0 修复（连续 10 局无 P0）
第 2–4 周    阶段四：后端迁云托管（本机验证 → 容器化与适配 → 部署 → 数据迁移）
第 3–4 周    阶段五：认证与发布准备（与阶段四并行；D 方案免备案）
第 4–5 周    阶段六：提审与发布
第 5 周起    阶段七：运营与迭代
```

**关键路径变成阶段四的「容器化 + callContainer 适配」**（约 2–3 周）。选 D 之后不再有 20 天的备案等待，这也是选它的主要收益。

> 如果阶段四改回方案 C，则关键路径重新变成备案（15–20 天），时间线整体后移约 3 周。

# 回到验收版（提交给老师用这个）
