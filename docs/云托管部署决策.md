# 微信云托管部署决策（方案 D 落地版）

> 状态：设计定稿，**尚未在云托管上实测**。构建阶段的报错以云托管日志为准，按第 5 节迭代。

---

## 1. 三个决定

| 决定 | 选择 | 理由 |
| --- | --- | --- |
| 容器形态 | **单服务、单容器** | 云托管一个服务一个容器；拆多服务要多套配置，先用最简单形态跑通 |
| Storage 后端 | **CFS 目录**（`/var/lib/storage`） | 不依赖 COS 的签名与权限配置；画作是小文件，CFS 足够 |
| Realtime | **不部署** | 客户端本来就有 1–2 秒轮询兜底；少一个进程，容器更稳、内存更省 |

后续若要加 Realtime，单独加一个服务即可，不动现有结构。

## 2. 容器内进程

```
nginx :80  ──/rest/v1/*──────► postgrest :3000
           ──/auth/v1/*──────► gotrue    :9999
           ──/storage/v1/*───► storage-shim (deno) :9000
           ──/functions/v1/*─► supabase functions (deno) :9100
           ──/healthz────────► "ok"
```

| 进程 | 端口 | 来源 |
| --- | --- | --- |
| PostgreSQL 15 | 5432（仅本机） | `supabase/postgres:15.8.1.060` |
| PostgREST | 3000 | 官方镜像 COPY 出来 |
| GoTrue | 9999 | 官方镜像 COPY 出来 |
| storage-shim（自写） | 9000 | Deno 脚本，实现 upload/sign 两个接口 |
| Edge Functions | 9100 | Deno，跑仓库里 5 个函数 |
| nginx | **80** | 云托管端口填 80 |

### 为什么自己写 storage-shim

官方 Storage API 是 Node 应用，塞进 Postgres 镜像要再带一套 Node 运行时，镜像会很大且容易出问题。

而客户端只用两个接口：

```
POST /storage/v1/object/artworks/<path>       上传
GET  /storage/v1/object/sign/artworks/<path>  取签名地址
```

用一个 ~80 行的 Deno 脚本实现（写文件到 CFS、返回带 token 的直链），比塞官方组件简单得多。

## 3. 数据与持久化

| 数据 | 容器路径 | 持久化 |
| --- | --- | --- |
| Postgres 数据目录 | `/var/lib/postgresql/data` | **CFS 必挂** |
| 画作文件 | `/var/lib/storage` | **CFS 必挂** |
| 迁移标记表 | 数据库内 `schema_migrations_app` | 随库 |

**验收必测**：重启容器后数据还在。这是整个方案最容易翻车的一点。

## 4. 首次启动流程（entrypoint）

```
1. 若 $PGDATA 为空 → initdb
2. 启动 Postgres，等待就绪
3. 建库 breakice（若不存在）
4. 执行 supabase/local/00-supabase-shim.sql（补 auth/storage schema）
5. 按编号执行 26 支迁移（已有标记则跳过）
6. 依次拉起 postgrest / gotrue / storage-shim / functions
7. nginx 前台运行
```

> 云托管上的镜像若已自带 `auth`/`storage` schema，第 4 步会自动跳过（脚本用 `create ... if not exists`）。

## 5. 构建失败时的迭代方式

Dockerfile 里有多处 `COPY --from=<官方镜像>`，**二进制路径可能与假设不同**。构建报错时按下面顺序处理：

| 报错 | 处理 |
| --- | --- |
| `COPY failed: no such file` | 用 `docker run --rm <image> ls /` 查真实路径（或看该镜像文档），改路径重传 |
| 镜像拉取超时 | 云托管构建机在境内，Docker Hub 可能慢；可改用国内镜像源或把二进制放到仓库里 |
| 内存不足（OOM at build） | 拆成两个服务：`db` 直接跑官方镜像，`backend` 只跑 API 组件 |

## 6. 部署步骤（环境建好后）

1. 建服务 `backend`，公网开（调试期）、内网开
2. 选「手动上传代码包」→ 上传 `deploy/cloudrun/dist/cloudrun.zip`
3. 端口填 **80**
4. 环境变量按 `deploy/cloudrun/env.example` 填（`JWT_SECRET` 等必须改）
5. 挂 CFS：`/var/lib/postgresql/data`、`/var/lib/storage`
6. 规格 2 核 4 G；开启「超限按量」
7. 访问 `https://<默认域名>/healthz` 应返回 ok
8. 浏览器访问 `/rest/v1/rooms?select=id&limit=1`，带 `apikey` 头，应返回 `[]` 或数据
9. 客户端改 `VITE_SUPABASE_URL` 指向默认域名（先直连验证），跑一局
10. 验证通过后：客户端改 `callContainer`，云托管**关闭公网访问**
