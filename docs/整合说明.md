
## 3. 已经接通的部分

1. **小程序入口**：`pages/home/index` 为启动页——上半屏形象自定义（6 张图层 + 5 组箭头）与昵称、下半屏创建 / 加入房间；形象与昵称自动保存。
2. **房间进入 C 模块**：房间等待区主持人控制台有「谁是卧底」「你画我猜谁是卧底」「题库管理」入口。
3. **房间进入 B 模块**：同一控制台的「你画我猜」进入 `/pages-draw/setup`，版本、人数、自定义题面由 B 的开设页自己管。
4. **玩家名单打通**：`app/src/services/gameEntry.ts` 把房间玩家按座位顺序转成昵称，带入 `/pages-uc/setup`、`/pages-uc/hybrid` 的 `names` 参数，C 的开设页据此预填座位（1 号位仍为主持人）。
5. **题库统一**：谁是卧底、融合玩法、真心话大冒险共用 C 的题库仓储；B 的你画我猜也通过 `bankRepo()` 从 `draw` 集合抽词（210 条），三方的词都来自同一份题库代码。
6. **题库规模**：`undercover-pairs` 157 + `english-pairs` 60 + `draw-words` 210 + `truth` 69 + `dare` 52 = **548 条**（其中中文原创 488 条，加 60 条英文词对）。
7. **设计变量在微信端可用**：D 的 `styles/tokens.scss` 从 `:root` 改为 `page`，因为 WXSS 不支持 `:root`；H5 构建时 uni-app 会映射到 `uni-page-body`，两端都已验证生效。

## 4. 尚未实现（明确标注，不是完成状态）

1. **微信小程序内的多人实时同步还没接通。** C 的引擎支持固定玩家多设备流程，但传输层只有 `app/dev` 的本地联调服务（`/__c1_mock/*`），只在 `npm run dev:players` 的 H5 预览里可用；真实实现是 A 的 `UcPlayerPort`。
2. **因此小程序里点「创建多设备联调游戏」会提示需要 H5 预览**，开设页已在小程序端显式标注。
3. **B 的你画我猜是本机房间**（`LocalDrawRoomBackend`）：同一台设备上只有「我」实际作画，其余座位到点自动轮过；真上传、真频道、排行榜落库要等 A。
4. **B 的画布在 H5 里不能作画**：`<canvas type="2d">` 的节点查询是小程序能力，必须在微信开发者工具里验证。
5. **融合玩法的画布仍是 C 的模拟适配器**（`MockDrawingAdapter.vue`）。B 交的是独立游戏页的画布组件，两处还没有合并成一个。
6. **头像只在 D 的页面展示**：C 与 B 的玩家数据都只有 `id` / `name`，所以他们的页面内不显示 D 的自定义形象。
7. **房间与在线状态仍是 D 的 Mock service**，没有 Supabase RPC / Realtime / 微信登录。
8. **Gitee CI 未激活**：`scripts/ci.sh` 与 `.gitee/ci-job.json` 是可执行脚本与配置说明，需要仓库管理员在 Gitee 后台绑定。

## 6. 运行方式

```powershell
Set-Location D:\1\break-ice-hall\app
npm install
npm run dev:mp-weixin      # 微信小程序开发（用微信开发者工具导入 app\dist\dev\mp-weixin）
npm run build:mp-weixin    # 微信小程序构建
npm run dev:h5             # H5 预览（画布类功能要回开发者工具看）
npm run dev:players        # H5 多设备联调（谁是卧底 / 融合玩法需要它）
npm run type-check
npm run test
npm --prefix app run verify   # 在仓库根目录跑完整流水线
```

微信开发者工具导入目录：

- 构建版：`D:\1\break-ice-hall\app\dist\build\mp-weixin`
- 开发版：`D:\1\break-ice-hall\app\dist\dev\mp-weixin`

AppID 在 `app/src/manifest.json` 的 `mp-weixin.appid` 填写；留空时开发者工具可用测试号预览。
